# Spec Delta: payments

## Purpose

Позволяет продавцу подключить ЮKassa, а покупателю — оплатить заказ
своего магазина. Платформа не хранит карточные данные и не принимает
деньги на свой счёт; в Sprint 3 используется fake/sandbox-провайдер.

## ADDED Requirements

### Requirement: Подключение платёжного аккаунта продавца

Система SHALL позволять авторизованному продавцу подключить один
платёжный аккаунт ЮKassa к своему магазину, подписать его на вебхуки и
хранить только ограниченный токен в зашифрованном виде.

#### Scenario: Успешное подключение

- **WHEN** продавец запрашивает подключение, подтверждает согласие у
  провайдера, а обмен кода и подписка на вебхуки прошли
- **THEN** система сохраняет зашифрованный токен, account id,
  `isTest`-флаг и статус `active`, а в админке показывает «Подключено»

#### Scenario: Не удалось подписать на вебхуки

- **WHEN** OAuth прошёл, но `subscribeWebhooks` вернул ошибку
- **THEN** новая версия получает `error`, текущий active-аккаунт (если
  был) не меняется, платежи по нему продолжают работать, UI просит
  повторить подключение

#### Scenario: Тестовый магазин

- **WHEN** провайдер вернул `isTest=true`
- **THEN** в `PAYMENTS_ENV=live` подключение отклоняется со статусом
  `error`, fake-провайдер запрещён; `sandbox` (preview) и `test`
  (CI/локально) разрешают тестовый контур; `NODE_ENV` не используется

#### Scenario: Повторное подключение

- **WHEN** продавец повторно проходит подключение
- **THEN** создаётся новая версия аккаунта, старая становится
  `superseded`, её токен остаётся для pending-платежей, второй active
  аккаунт не появляется

#### Scenario: Невалидный state

- **WHEN** callback приходит без сессии продавца, с истёкшим/поддельным
  state или чужим seller_id
- **THEN** система возвращает 400/401/403 и не меняет аккаунт

#### Scenario: Отключение с активным платежом

- **WHEN** продавец отключает аккаунт, пока есть платёж в
  `pending`/`manual_review`
- **THEN** система возвращает 409 и не отключает аккаунт

#### Scenario: Отключение без активных платежей

- **WHEN** продавец отключает аккаунт без активных платежей
- **THEN** статус становится `disabled`, токен сохраняется для поздних
  вебхуков и reconcile, новые платежи не создаются

#### Scenario: Без сессии

- **WHEN** ручки подключения вызываются без сессии продавца
- **THEN** система возвращает 401

### Requirement: Создание платежа

Система SHALL создавать платёж на полную сумму заказа только для
покупателя этого заказа и только при активном аккаунте продавца.

#### Scenario: Успешное создание

- **WHEN** покупатель отправляет `POST /orders/:id/payments` с валидным
  `Idempotency-Key` для своего заказа в статусе `new`
- **THEN** система создаёт платёж `pending`, переводит заказ в
  `payment_pending` и возвращает `confirmationUrl`

#### Scenario: Нет или невалидный Idempotency-Key

- **WHEN** заголовок отсутствует или содержит не UUID
- **THEN** система возвращает 400 и не вызывает провайдера

#### Scenario: Чужой заказ

- **WHEN** покупатель пытается оплатить заказ другого покупателя
- **THEN** система возвращает 404 и не создаёт платёж

#### Scenario: Заказ уже оплачен

- **WHEN** покупатель создаёт платёж **с новым** `Idempotency-Key` для
  заказа в статусе `paid`
- **THEN** система возвращает 409 `order_already_paid` и не вызывает
  провайдера; `paid` терминален

#### Scenario: Продавец не подключил ЮKassa

- **WHEN** у продавца нет активного платёжного аккаунта
- **THEN** система возвращает 409 `seller_payment_unavailable` и не
  создаёт платёж

#### Scenario: Нулевая сумма

- **WHEN** `orders.total_kopecks` равен 0
- **THEN** система возвращает 409 `zero_amount` и не создаёт платёж

#### Scenario: Провайдер недоступен при создании

- **WHEN** провайдер отвечает 5xx/timeout (исход вызова неизвестен)
- **THEN** система оставляет попытку `pending`, возвращает 502, заказ
  остаётся `new`; повтор с тем же ключом вызывает провайдера снова с
  тем же idempotency key, новый ключ получает 409 до reconcile

#### Scenario: Провайдер отклонил создание

- **WHEN** провайдер отвечает 401/403
- **THEN** аккаунт становится `error`, система возвращает 409
  `seller_payment_unavailable`

#### Scenario: Провайдер отклонил создание (4xx)

- **WHEN** провайдер отвечает другим явным 4xx и платёж не создан
- **THEN** система помечает попытку `failed`, возвращает 502, и новый
  ключ может создать новую попытку

#### Scenario: Слишком частые попытки

- **WHEN** покупатель превышает 5 попыток создания платежа в минуту
- **THEN** система возвращает 429 и не вызывает провайдера

### Requirement: Идемпотентность платежа

Система SHALL гарантировать один активный платёж на заказ и
идемпотентность повторного запроса с тем же `Idempotency-Key`.

#### Scenario: Повтор с тем же ключом в pending

- **WHEN** покупатель повторяет запрос с тем же `Idempotency-Key`, а
  платёж в `pending` уже имеет `provider_payment_id` и
  `confirmationUrl`
- **THEN** система возвращает существующий платёж и тот же
  `confirmationUrl`, независимо от статуса заказа, и не создаёт новый
  у провайдера

#### Scenario: Повтор после успешной оплаты

- **WHEN** тот же `Idempotency-Key` приходит после вебхука `paid`
- **THEN** система возвращает существующий платёж без `confirmationUrl`,
  а не 409 `order_already_paid`

#### Scenario: Повтор при ручном разборе

- **WHEN** тот же ключ приходит по платежу в `manual_review`
- **THEN** система возвращает 409 `payment_requires_review` без URL

#### Scenario: Повтор после сбоя провайдера

- **WHEN** тот же ключ повторяется после `failed` без provider id (явный 4xx)
- **THEN** система снова вызывает `createPayment` с тем же idempotency
  key и обновляет попытку; дубля списания нет

#### Scenario: Параллельные запросы

- **WHEN** два запроса с одним `Idempotency-Key` приходят одновременно
- **THEN** система сериализует их по заказу, создаёт один платёж и
  возвращает его обоим

#### Scenario: Новый ключ при активном платеже

- **WHEN** покупатель присылает новый `Idempotency-Key`, пока есть
  `pending` — с provider id или без него — независимо от статуса
  заказа (`new` или `payment_pending`)
- **THEN** система возвращает 409 `payment_in_progress` и не создаёт
  второй платёж до reconcile/manual_review

#### Scenario: Новый ключ при сироте после 5xx

- **WHEN** заказ остался `new`, а платёж после 5xx/timeout — `pending`
  или `manual_review`
- **THEN** новый ключ получает 409 (`payment_in_progress` или
  `payment_requires_review`), а не unique violation/500

#### Scenario: Новый ключ при ручном разборе

- **WHEN** по заказу есть `manual_review`
- **THEN** система возвращает 409 `payment_requires_review` и не
  создаёт второй платёж

### Requirement: Вебхук провайдера

Система SHALL обрабатывать вебхук ЮKassa идемпотентно, проверяя
платёж запросом к API провайдера, а не доверяя телу запроса.

#### Scenario: Успешная оплата

- **WHEN** провайдер присылает вебхук по существующему платежу и
  `getPayment` возвращает `succeeded` с суммой/валютой/заказом,
  совпадающими с БД
- **THEN** система под тем же order-lock переводит платёж в
  `succeeded`, заказ `payment_pending → paid`, фиксирует `paid_at` и
  возвращает 200

#### Scenario: Повтор вебхука

- **WHEN** тот же вебхук приходит повторно или параллельно
- **THEN** система не меняет сумму/статус повторно и возвращает 200

#### Scenario: Отменённый платёж

- **WHEN** `getPayment` возвращает `canceled` для заказа, который ещё
  не оплачен и не имеет другого активного/спорного платежа
- **THEN** система переводит платёж в `canceled`, заказ
  `payment_pending → new` и возвращает 200

#### Scenario: Отмена при другом активном платеже

- **WHEN** `canceled` приходит по старому платежу, пока есть другой
  активный/спорный платёж
- **THEN** система помечает только этот платёж `canceled` и не меняет
  статус заказа

#### Scenario: Несовпадение суммы

- **WHEN** сумма/валюта/orderId от провайдера не совпадает с БД
- **THEN** система помечает платёж `manual_review`, оставляет заказ
  `payment_pending`, блокирует новый платёж, пишет безопасный код
  `payment_amount_mismatch` и возвращает 200; событие финализировано,
  разбор — по runbook

#### Scenario: Неизвестный платёж

- **WHEN** вебхук приходит по `provider_payment_id`, которого нет в БД
- **THEN** система пишет `webhook_unknown_payment` и возвращает 503,
  чтобы провайдер повторил; reconcile ищет только строки с provider id,
  а 200 не возвращается, чтобы не потерять событие

#### Scenario: Невалидное тело

- **WHEN** тело вебхука не JSON, превышает лимит или не содержит id
- **THEN** система возвращает 400/413 и не вызывает провайдера

#### Scenario: Ошибка провайдера

- **WHEN** `getPayment` недоступен или отвечает ошибкой
- **THEN** система не меняет заказ, отвечает 502/503 и позволяет
  провайдеру повторить вебхук

#### Scenario: Потерянный вебхук

- **WHEN** платёж с provider id остаётся `pending`, а заказ
  `payment_pending` дольше 2 минут
- **THEN** reconcile под тем же order-lock вызывает `getPayment`,
  перечитывает платёж/заказ и применяет те же переходы; после рестарта
  API reconcile продолжает работу

#### Scenario: Сирота без provider id

- **WHEN** платёж остаётся `pending` без provider id дольше 15 минут
- **THEN** reconcile переводит его в `manual_review`, чтобы исход
  неизвестного вызова не привёл к второму списанию; новый платёж
  блокируется до ручного разбора

### Requirement: Ручной разбор платежа

Система SHALL удерживать платёж в `manual_review` до явного ручного
разбора и не позволять обойти его новым платежом.

#### Scenario: Платежа у провайдера нет

- **WHEN** ops по `metadata.orderId`/`paymentId` не находит платёж у
  провайдера
- **THEN** платёж становится `canceled`, заказ возвращается в `new`,
  новый платёж разрешён

#### Scenario: Подтверждён возврат

- **WHEN** ops подтверждает возврат по `manual_review`; деньги
  возвращает продавец/ops в кабинете ЮKassa вне платформы
- **THEN** платёж становится `canceled`, заказ возвращается в `new`,
  новый платёж разрешён

#### Scenario: Подтверждена оплата

- **WHEN** ops подтверждает, что деньги получены
- **THEN** платёж становится `succeeded`, заказ `paid`, новый платёж
  запрещён

#### Scenario: Попытка обойти разбор

- **WHEN** покупатель создаёт новый платёж, пока есть `manual_review`
- **THEN** система возвращает 409 `payment_requires_review`

### Requirement: Статус оплаты заказа

Система SHALL показывать статус оплаты покупателю и продавцу заказа
без раскрытия платёжных секретов.

#### Scenario: Покупатель смотрит свой заказ

- **WHEN** покупатель запрашивает `GET /orders/:id/payment`
- **THEN** он видит активный платёж (`pending`/`manual_review`), иначе
  последний терминальный; `confirmationUrl` — только для `pending`;
  если платежей нет — `payment: null`

#### Scenario: Продавец смотрит заказ магазина

- **WHEN** продавец запрашивает `GET /seller/orders/:id/payment`
- **THEN** он видит статус и сумму, но не `confirmationUrl` и не токен

#### Scenario: Чужой заказ

- **WHEN** оплату запрашивает покупатель или продавец чужого заказа
- **THEN** система возвращает 404

#### Scenario: Ожидание возврата с оплаты

- **WHEN** покупатель возвращается на `/orders/:id?payment=return`
- **THEN** UI показывает «Проверяем оплату», опрашивает статус и
  обновляет заказ после `paid`; ключ попытки сохраняется для retry

### Requirement: Приватность и кэш

Система SHALL не хранить карточные данные и не писать платёжные
секреты/PII в логи; ответы с оплатой не кэшируются.

#### Scenario: Карточные данные

- **WHEN** покупатель оплачивает заказ
- **THEN** ввод карты происходит на hosted page провайдера, а
  платформа хранит только id/статус/сумму платежа

#### Scenario: Логи

- **WHEN** создание платежа или вебхук завершается ошибкой
- **THEN** лог содержит `payment_id`/`order_id`/`status`/`code`, но не
  телефон, комментарий, токен, тело вебхука или карточные данные

#### Scenario: Кэш

- **WHEN** любой ответ платежей отдаётся клиенту
- **THEN** он содержит `Cache-Control: no-store`

#### Scenario: Частота вебхуков

- **WHEN** один IP превышает 60 вебхуков в минуту
- **THEN** система возвращает 429 и не обрабатывает событие

### Requirement: Переходы статуса заказа при оплате

Система SHALL менять статус заказа только по правилам оплаты и под
order-lock, общим для create и webhook.

#### Scenario: Начало оплаты

- **WHEN** провайдер успешно создал платёж и система сохранила
  provider id/URL
- **THEN** заказ условно переходит `new → payment_pending`; при
  5xx/timeout заказ остаётся `new`

#### Scenario: Успех

- **WHEN** платёж подтверждён
- **THEN** заказ переходит `payment_pending → paid`; `paid` терминален

#### Scenario: Неудача

- **WHEN** платёж отменён до оплаты и других активных платежей нет
- **THEN** заказ возвращается `payment_pending → new` и можно
  попробовать снова

#### Scenario: Заказ payment_pending без активного платежа

- **WHEN** заказ в `payment_pending`, но active/`manual_review` платежа
  нет
- **THEN** новый ключ получает 409 `invalid_order_transition`, пока
  reconcile/manual review не приведёт статус в порядок

#### Scenario: Гонка create и webhook

- **WHEN** `succeeded`-вебхук приходит одновременно с созданием нового
  ключа
- **THEN** оба обработчика берут один order-lock; create перечитывает
  заказ под lock, видит `paid` и не вставляет второй платёж

#### Scenario: Повтор с существующим ключом в гонке

- **WHEN** повтор с уже созданным ключом приходит после `paid`
- **THEN** lookup по ключу выполняется до статусного гейта и возвращает
  существующий платёж, а не 409

#### Scenario: Недопустимый переход

- **WHEN** код пытается перевести заказ из `paid` в
  `payment_pending` или из `new` в `paid` без платежа
- **THEN** система возвращает 409 `invalid_order_transition` и не
  меняет данные

#### Scenario: Повторная проверка под lock

- **WHEN** create получает order-lock после успешного вебхука
- **THEN** он перечитывает заказ под lock, видит `paid` и возвращает
  409 до вставки второй строки `payments`
