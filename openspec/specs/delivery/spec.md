# delivery Specification

## Purpose

Позволяет покупателю выбрать ПВЗ и стоимость доставки при checkout, а
продавцу — создать отправление СДЭК или ввести трек вручную; покупатель
и продавец видят трек и статус.

## Requirements

### Requirement: Габариты товара и город продавца

Система SHALL требовать вес/габариты физического товара и город отправки
магазина для расчёта доставки.

#### Scenario: Данные заполнены

- **WHEN** у товара есть `weight_g`/габариты, у магазина — `city_code`
- **THEN** checkout может рассчитать доставку

#### Scenario: Нет габаритов

- **WHEN** физический товар без веса/габаритов попадает в quote/checkout
- **THEN** система возвращает 409 `delivery_dimensions_missing` и не
  создаёт заказ

#### Scenario: Нет города магазина

- **WHEN** у магазина не заполнен город отправки
- **THEN** система возвращает 409 `shop_city_missing`

### Requirement: ПВЗ и расчёт доставки

Система SHALL показывать города/ПВЗ СДЭК и рассчитывать стоимость/срок
по каждому магазину.

#### Scenario: Успешный quote

- **WHEN** покупатель выбирает город и ПВЗ и запрашивает quote для
  доступных товаров
- **THEN** система возвращает по магазину тариф, цену и срок

#### Scenario: Несколько магазинов

- **WHEN** в корзине товары разных магазинов
- **THEN** quote считается отдельно для каждого магазина; ПВЗ общий

#### Scenario: ПВЗ не из города

- **WHEN** `pointCode` не принадлежит `cityCode`
- **THEN** система возвращает 409 `delivery_point_invalid` и не считает
  quote

#### Scenario: CDEK недоступен

- **WHEN** провайдер отвечает ошибкой/таймаутом
- **THEN** система возвращает 502 `delivery_unavailable` и не создаёт
  заказ

#### Scenario: Слишком часто

- **WHEN** клиент превышает 30 quote-запросов в минуту
- **THEN** система возвращает 429

### Requirement: Checkout с доставкой

Система SHALL включать проверенную доставку в заказ и итоговую сумму.

#### Scenario: Успешный checkout

- **WHEN** покупатель отправляет checkout с `delivery` (city/point/
  recipientName/quoteToken)
- **THEN** система проверяет подписанный quote (TTL/hash/city/point),
  создаёт заказы с `delivery_kopecks` и
  `total_kopecks = items + delivery`

#### Scenario: Quote устарел

- **WHEN** quoteToken истёк или состав товаров изменился
- **THEN** система возвращает 409 `delivery_quote_stale` и не создаёт
  заказ

#### Scenario: Нет доставки

- **WHEN** покупатель оформляет физический заказ без выбранной доставки
- **THEN** система возвращает 409 `delivery_required` и не создаёт заказ

#### Scenario: Цена клиента

- **WHEN** клиент присылает свою цену доставки
- **THEN** система её игнорирует и использует серверный quote

#### Scenario: Доставка недоступна

- **WHEN** quote/размеры/город недоступны
- **THEN** система возвращает 409/502 и не создаёт частичный заказ

### Requirement: Отправление СДЭК

Система SHALL создавать отправление СДЭК для оплаченного заказа через
платформенный аккаунт и обрабатывать асинхронный ответ.

#### Scenario: Seller видит тарифы

- **WHEN** продавец открывает оплаченный заказ
- **THEN** система возвращает тарифы CDEK от города/ПВЗ магазина до
  ПВЗ покупателя и помечает оплаченный тариф/цену

#### Scenario: Успешное создание

- **WHEN** продавец создаёт отправление с оплаченным `tariffCode`
- **THEN** система вызывает CDEK с `number=order-{id}` и
  `shipment_point`, сохраняет provider order id/номер и ставит delivery
  `created`

#### Scenario: Локальный ответ на создание

- **WHEN** CDEK принимает `POST /v2/orders` асинхронно и отвечает `202`
- **THEN** API обрабатывает `202` внутри, сохраняет provider id/номер и
  отвечает продавцу `201` со snapshot; `202` — ответ провайдера, а не
  статус локального API

#### Scenario: Другой тариф

- **WHEN** продавец выбирает тариф, отличный от оплаченного, или цена
  CDEK изменилась
- **THEN** система возвращает 409 `delivery_tariff_mismatch`, не
  создаёт отправление и не меняет `price_kopecks`/`total`; разница —
  ручной разбор

#### Scenario: Заказ не оплачен

- **WHEN** продавец пытается создать отправление для неоплаченного
  заказа
- **THEN** система возвращает 409 `delivery_not_paid`

#### Scenario: Старый заказ без доставки

- **WHEN** paid-заказ создан до delivery и не имеет
  `order_deliveries`/ПВЗ получателя
- **THEN** CDEK create возвращает 409 `delivery_snapshot_missing`;
  доступен только manual carrier/track

#### Scenario: Чтение старого заказа без snapshot

- **WHEN** продавец запрашивает `GET /seller/orders/:id/delivery` для
  paid-заказа без `order_deliveries`
- **THEN** система возвращает 404 и не раскрывает чужую/несуществующую
  доставку; manual carrier/track остаётся доступен через PATCH

#### Scenario: Повтор

- **WHEN** продавец повторяет создание
- **THEN** система возвращает существующее отправление, не создавая
  второе

#### Scenario: Провайдер недоступен

- **WHEN** CDEK отвечает 5xx/timeout
- **THEN** система возвращает 502, не теряет заказ и сначала
  reconcile-ит по `number`; manual доступен только если CDEK-заказа
  точно нет

### Requirement: Ручной трек

Система SHALL позволять продавцу ввести перевозчика и трек вручную,
если провайдер не настроен (manual) или подтверждено, что CDEK-заказ
не создан. При недоступном CDEK manual блокируется до reconcile, чтобы
не создать дубль.

#### Scenario: Ручной трек

- **WHEN** продавец сохраняет carrier/track для оплаченного заказа, а
  CDEK-отправления точно нет
- **THEN** delivery получает `manual`, покупатель видит трек

#### Scenario: CDEK недоступен

- **WHEN** поиск CDEK-заказа завершился сетевой ошибкой/5xx
- **THEN** manual возвращает 502 `delivery_provider_error`; продавец
  повторяет после reconcile/поддержки

#### Scenario: CDEK уже создан

- **WHEN** у заказа есть provider order id/номер CDEK
- **THEN** manual-трек возвращает 409 `delivery_already_exists` и не
  перезаписывает отправление

#### Scenario: Уже есть CDEK

- **WHEN** у заказа уже есть CDEK-отправление
- **THEN** manual-трек не перезаписывает его без явного решения

### Requirement: Трек и статусы

Система SHALL обновлять статус доставки по вебхуку/опросу и показывать
его покупателю и продавцу.

#### Scenario: Вебхук

- **WHEN** приходит `ORDER_STATUS`
- **THEN** система проверяет заказ через `GET /v2/orders/{uuid}`,
  сверяет номер и идемпотентно сохраняет событие/статус

#### Scenario: Неизвестный заказ

- **WHEN** вебхук ссылается на неизвестный локальный заказ
- **THEN** система возвращает 404, пишет код и не создаёт событие

#### Scenario: Ошибка проверки

- **WHEN** `GET /v2/orders/{uuid}` недоступен/таймаут
- **THEN** система возвращает 502 и не применяет статус; провайдер
  повторит доставку

#### Scenario: Подписка

- **WHEN** приложение стартует с CDEK
- **THEN** оно проверяет одну подписку `ORDER_STATUS` на
  `/delivery/cdek/webhook`; при наличии двух чужих подписок не создаёт
  третью и пишет ops-ошибку

#### Scenario: Повторный старт и один инстанс

- **WHEN** API стартует повторно и подписка `ORDER_STATUS` на тот же URL
  уже существует
- **THEN** система не создаёт вторую подписку; v1 работает с одним
  API-процессом, распределённой блокировки подписки нет

#### Scenario: Общая тестовая учётная запись

- **WHEN** API запускается с общей тестовой учётной записью CDEK, у
  которой уже четыре подписки
- **THEN** `ensureOrderStatusWebhook` не изменяет и не удаляет их; при
  совпадении с текущим URL — no-op, иначе пишет
  `delivery_webhook_subscription_failed reason=conflict`; для проверки
  вебхука используется отдельный тестовый аккаунт

#### Scenario: История событий продавцу

- **WHEN** продавец запрашивает `GET /seller/orders/:id/delivery`
- **THEN** ответ `{delivery, events}` содержит не более 50 событий в
  порядке `occurred_at DESC, id DESC`, только `statusCode`,
  `statusName` и `occurredAt`; `payloadHash`, raw payload и чужие ПДн
  не возвращаются

#### Scenario: Потерянный вебхук

- **WHEN** delivery остаётся `created`/`in_transit` > 2 минут
- **THEN** reconcile опрашивает CDEK (порог 2 минуты) и применяет
  статус, включая `delivered`

#### Scenario: Нет отправления

- **WHEN** delivery остаётся `quoted` без отправления
- **THEN** статус не меняется автоматически; UI показывает «Ожидает
  отправки», система не переводит delivery в `failed`; создание
  отправления — отдельное действие продавца (см. сценарии выше)

#### Scenario: Неизвестный статус

- **WHEN** CDEK вернул неизвестный код
- **THEN** система сохраняет raw code, ставит `in_transit` и пишет
  безопасный лог

#### Scenario: Доставлено

- **WHEN** CDEK вернул `DELIVERED`
- **THEN** delivery `delivered`, событие сохранено

### Requirement: Authz и PII

Система SHALL показывать доставку только покупателю заказа и продавцу
магазина и не писать PII в логи.

#### Scenario: Чужой заказ

- **WHEN** покупатель/продавец запрашивает чужую доставку
- **THEN** система возвращает 404

#### Scenario: Логи

- **WHEN** создание/вебхук завершается ошибкой
- **THEN** лог содержит order/delivery id, provider, status/code; без
  имени, телефона, адреса и raw payload

#### Scenario: Кэш

- **WHEN** отдаётся ответ с доставкой
- **THEN** он содержит `Cache-Control: no-store`

#### Scenario: Live PII запрещён

- **WHEN** `DELIVERY_LIVE_PII=false` (default)
- **THEN** live-контур не принимает реальные имена/телефоны; preview
  работает только с вымышленными тестовыми данными

### Requirement: Провайдер-нейтральность

Система SHALL хранить доставку независимо от перевозчика, чтобы Ozon
подключить вторым адаптером.

#### Scenario: Смена адаптера

- **WHEN** добавляется Ozon
- **THEN** заказ/UI/статусы используют `DeliveryProvider`, а не
  CDEK-специфичные поля

#### Scenario: Manual

- **WHEN** выбран manual-провайдер
- **THEN** заказ и UI работают без CDEK-полей
