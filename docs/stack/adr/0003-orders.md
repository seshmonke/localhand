# ADR 0003: заказы, PII и отсутствие оплаты

Статус: accepted.
Дата: 2026-11-27.
Владелец: Local Hand.

## Контекст

- Sprint 2 закрывает buyer-core: покупатель находит товар, собирает
  корзину, оформляет заказы и видит их; продавец видит заказы своего
  магазина. Поведение — `openspec/specs/checkout-orders/spec.md`,
  реализация — архив `2026-11-27-05-checkout-orders`.
- Авторизация — телефонный OTP и JWT-cookie из ADR 0002; отдельной
  buyer-роли нет: покупатель — любой `users`, продавец — пользователь
  со строкой в `sellers`.
- v1 работает без оплаты и доставки: заказ — заявка продавцу, деньги и
  чеки не проходят через платформу. Это решение продукта, а не
  временная заглушка в коде.
- Один API-процесс Fastify + PostgreSQL 18, без Redis и отдельного
  job-сервера (`docs/stack/adr/0001-stack.md`). Репозиторий публичный,
  тестовые данные — только вымышленные.

## Решение

### Заказ — заявка без оплаты и резерва

- `POST /checkout` создаёт один заказ на каждый магазин из доступных
  товаров. Платформа не принимает деньги, не резервирует товар и не
  обещает наличие: два покупателя могут оформить заявку на одну вещь,
  продавец подтверждает вручную.
- Оплата, доставка, отмена и статусы после `new` — отдельные change.
  Пока они не подключены, API и UI прямо говорят «оплата и доставка не
  подключены». 54-ФЗ/ККТ и эквайринг не применяются, пока платформа не
  принимает платёж; схема оплаты и договор с эквайером — решение
  владельца до следующего change (`docs/legal/context.md`).

### Схема и миграция `0003`

- `orders`: `id`, `buyer_user_id` (FK `users`, `ON DELETE RESTRICT`),
  `shop_id` (FK `shops`, `ON DELETE RESTRICT`), `status`
  (`order_status = 'new'`, default `new`), `total_kopecks` (`bigint`,
  `>= 0`), `buyer_phone` (snapshot телефона сессии), `comment` (nullable,
  `<= 500`), `client_checkout_id` (`uuid`), `created_at`, `updated_at`.
- `order_items`: `id`, `order_id` (FK `orders`, `ON DELETE CASCADE`),
  `product_id` (FK `products`, `ON DELETE SET NULL`), `name`,
  `price_kopecks` (`>= 0`), `quantity` (`= 1`). Название и цена —
  snapshot на момент checkout, а не ссылка на живую карточку.
- Уникальность `(buyer_user_id, client_checkout_id, shop_id)` — страховка
  идемпотентности на уровне БД. Индексы:
  `orders(buyer_user_id, created_at desc)`,
  `orders(shop_id, created_at desc)`, `order_items(order_id)`.
- Миграция аддитивная. Down SQL и порядок отката (остановить трафик,
  выгрузить ПДн, удалить таблицы, почистить журнал drizzle) —
  `docs/stack/runbooks/orders-rollback.md`.

### Checkout и идемпотентность

- Тело: `{ items: [{ productId }], comment?, clientCheckoutId }`.
  `items` — 1–50 уникальных `productId`, `comment` — trim, до 500
  символов, `clientCheckoutId` — UUID; невалидное — `400`.
- Без сессии — `401`. Лимит — 10 checkout в минуту на `user_id`,
  превышение — `429`; IP в ключ не входит, потому что ручка доступна
  только с сессией.
- Товары и магазины читаются в одной транзакции с условиями
  `products.status = 'published'` и `shops.status = 'published'`.
  Строки товаров блокируются `FOR UPDATE OF products` в порядке
  `products.id`; если хотя бы один товар недоступен — `409
  product_unavailable`, частичного заказа нет.
- Заказы группируются по `shop_id`; total считается на сервере по
  ценам из БД, не из корзины. `buyer_phone` берётся из сессии.
- Повтор с тем же `(buyer_user_id, client_checkout_id)` возвращает уже
  созданный набор заказов, даже если `items` в повторе другие: ключ
  идемпотентности — только UUID, новый состав требует нового UUID.
  Конкурентные запросы с одним ключом сериализуются транзакционным
  advisory lock `pg_advisory_xact_lock(hashtextextended("userId:uuid"))`,
  который берётся первым действием транзакции; уникальный индекс —
  страховка на случай гонки. UUID приводится к нижнему регистру до
  сравнения и записи.

### Статусы

- В v1 единственный статус — `new`. Значение хранится в PostgreSQL enum,
  чтобы следующие change добавляли переходы (`confirmed`, `cancelled`
  и т.п.) миграцией, а не строкой без ограничений.
- Клиент не может менять статус: PATCH-ручек заказа нет. Переходы
  появятся вместе с оплатой/доставкой и отдельным change.

### Authz

- Публичных ручек заказов нет. `GET /orders/mine` и `GET /orders/:id`
  фильтруют по `buyer_user_id` из сессии; чужой заказ — `404`, не
  `403`, чтобы не раскрывать существование id.
- `GET /seller/orders` и `GET /seller/orders/:id` фильтруют через
  `shops.seller_id → sellers.user_id`; чужой заказ — `404`. Продавец
  без магазина получает `200 { orders: [] }` и onboarding в UI.
- `POST /checkout` и все чтения требуют валидную cookie; иначе `401`
  без деталей. Телефон и комментарий не попадают в публичные ответы.
- Все ответы плагина заказов отдаются с `Cache-Control: no-store`:
  в них ПДн, их нельзя кэшировать браузеру, прокси и CDN.

### PII и логи

- Храним минимум: телефон покупателя (snapshot), необязательный
  комментарий, snapshot названия/цены товара. Имя, адрес, email,
  паспорт, платёжные данные не собираются.
- Видят телефон и комментарий только покупатель этого заказа и продавец
  магазина этого заказа. Публичного доступа и публичных ссылок на заказ
  нет.
- Ошибки checkout/orders логируются как `{ code }` + generic-сообщение;
  телефон, комментарий, тело запроса и OTP в лог не попадают. Это
  проверяется source-аудитом и runtime-тестом с принудительным `500`
  (`apps/api/src/orders/orders.logs.test.ts`).
- Access-лог Fastify содержит метод, URL и статус, но не тело запроса;
  URL заказов не содержит телефона/комментария. Retention логов — общая
  политика эксплуатации.
- Комментарий — свободный текст: покупатель может сам вписать лишние
  ПДн. В оферте/политике и подсказке формы фиксируем, что комментарий
  видит продавец и что лишние данные писать не нужно.
- Dev OTP, фейковые телефоны и магазины в e2e; скриншоты/видео без
  реальных ПДн.

### Наблюдаемость

- На каждый `500` — одна запись `{ code }` без ПДн; этого достаточно для
  диагностики на одном инстансе v1. Метрики checkout (счётчики
  успех/409/429), трейсы и алерты — P3 до публичного запуска.

## Альтернативы

- **Guest checkout.** Отклонено спецификацией checkout-orders: без
  сессии нельзя показать покупателю его заказы и связать телефон.
- **Оплата на платформе сразу.** Отклонено: требует договора с
  эквайером, 54-ФЗ/ККТ, схемы расчётов и юридического решения; вне
  скоупа buyer-core.
- **Резерв товара и блокировка остатков.** Отклонено для v1: нет
  модели склада/количества; заказ — заявка. Вернуться вместе с оплатой.
- **Один заказ на все магазины.** Отклонено: у каждого магазина свой
  продавец, свои статус и коммуникация; заказ на магазин даёт понятный
  scope authz.
- **Публичная ссылка на заказ с токеном.** Отклонено: лишний секрет и
  риск утечки ПДн; доступ только по сессии.
- **Идемпотентность по хешу корзины.** Отклонено: хеш меняется от
  любого изменения цены/названия и не переживает повтор; явный
  `clientCheckoutId` — контракт клиента.
- **Статусы оплаты/доставки сразу.** Отклонено: поведение без оплаты
  было бы фиктивным; enum расширяется отдельным change.
- **Redis для идемпотентности/лимитов.** Отклонён для v1: PostgreSQL
  advisory lock и in-memory лимитер достаточны для одного инстанса.

## Последствия

- Плюсы: buyer-core проверен сквозным API и браузерным e2e; деньги не
  проходят через платформу, поэтому нет 54-ФЗ/эквайринга в v1; ПДн
  минимизированы, ответы не кэшируются, логи без ПДн.
- Минусы: нет резерва — возможны две заявки на одну вещь; статус только
  `new`, продавец обрабатывает заказ вне системы; отмена заказа
  отсутствует.
- Минусы: in-memory rate limit сбрасывается при рестарте и не общий для
  нескольких инстансов; метрик и трейсов нет — P3.
- Риск: free-text комментарий может содержать лишние ПДн; до публичного
  запуска нужны политика, согласие на передачу телефона продавцу,
  retention и порядок удаления заказов.
- Риск: `ON DELETE RESTRICT` у `buyer_user_id`/`shop_id` не даёт удалить
  пользователя/магазин с заказами; удаление ПДн по запросу субъекта
  потребует отдельной процедуры (анонимизация/каскад) — до публичного
  запуска.
- Откат: revert кода + down SQL из runbook; данные заказов не
  восстанавливаются автоматически, выгружаются до удаления.
