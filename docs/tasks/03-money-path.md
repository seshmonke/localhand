# Спринт 3: money-path

Статус: **BUILDING**, cycle 5. S3-1 закрыт; `06-payments` в архиве; S3-2 `07-delivery` в работе.
Дата планирования: 27.11.2026.
Направление: №2 — подключить продавца к деньгам и доставке
(`docs/tasks/INDEX.md`).
Changes: `06-payments`, `07-delivery`, `08-order-lifecycle`,
`09-orders-pagination` (создаются по волнам).

## Sprint Goal

Покупатель оплачивает заказ на сайте продавцу в тестовом контуре
ЮKassa, продавец видит оплату, оформляет отправление СДЭК и ведёт заказ
до трек-номера и статуса доставки. Реальные деньги, ключи и ПДн
покупателей в спринте не используются.

## PBI

### S3-1. Payments: ЮKassa sandbox

Change: `06-payments` (capability `payments`).
Зачем: заказ перестаёт быть заявкой и получает оплату напрямую
продавцу; платформа не держит деньги.

AC:
- [x] Продавец подключает свой магазин к ЮKassa партнёрской схемой;
      платформа хранит ограниченный токен в зашифрованном виде (keyring),
      подписывает магазин на вебхуки и версионирует аккаунт при
      переподключении; статус/тестовый бейдж видны в админке.
- [x] Покупатель инициирует оплату своего неоплаченного заказа,
      получает `confirmationUrl`; чужой заказ — 404, неоплатимый
      статус — 409, без сессии — 401. Сбой провайдера: 4xx — `failed`
      и новая попытка, 5xx/timeout — `pending` + 502, тот же ключ
      ретраит, новый ключ ждёт reconcile/manual_review.
- [x] Вебхук провайдера проверяет платёж запросом к API, сверяет
      сумму/валюту/заказ и переводит заказ в `paid`; неизвестный платёж
      получает 503, чтобы create успел закоммитить, pending добирает
      reconcile; mismatch — `manual_review` с блокировкой нового
      платежа; повтор и параллельные вебхуки идемпотентны, гонка
      create/webhook не откатывает `paid`.
- [x] Карточные данные не сохраняются и не логируются; ответы с
      платёжными данными — `no-store`; PII в логи не попадает.
- [x] Тесты: fake-провайдер на границе адаптера, DB-интеграция
      идемпотентности/amount mismatch, browser e2e оплаты; sandbox
      smoke — после получения тестовых ключей владельцем (P3).

Зависимости: тестовые ключи/партнёрская схема ЮKassa — владелец.
Без ключей: адаптер + fake, live smoke не блокирует merge.

### S3-2. Delivery: СДЭК test contour

Change: `07-delivery` (capability `delivery`).
Зачем: физический заказ получает расчёт, отправление и трек.

AC:
- [ ] У товара есть вес и габариты; checkout собирает адрес
      получателя/ПВЗ с валидацией; поля PII минимизированы.
- [ ] Для оплаченного заказа продавец получает расчёт СДЭК, выбирает
      тариф, создаёт отправление и видит трек-номер.
- [ ] Статус доставки приходит по вебхуку/опросу и отражается в
      заказе покупателя и продавца.
- [ ] Чужой заказ/магазин — 404; адрес и телефон не попадают в логи
      и публичные ответы; ответы `no-store`.
- [ ] Тесты: fake СДЭК на границе адаптера, DB-интеграция, e2e
      оформления; реальный тестовый аккаунт — после ключей владельца.

Зависимости: тестовый аккаунт СДЭК — владелец; юридическое решение
по сбору адреса — до реальных ПДн.

### S3-3. Order lifecycle

Change: `08-order-lifecycle` (delta `payments` + `checkout-orders`).
Зачем: оплата и доставка получают явные переходы, а не один `new`.

AC:
- [ ] Статусы: `new` → `paid` → `shipped` → `delivered`; отмена
      неоплаченного — `cancelled`; недопустимый переход — 409.
- [ ] Продавец отмечает отправление; покупатель видит статус и трек;
      платёж и доставка обновляют статус только идемпотентно.
- [ ] История переходов хранится отдельно и доступна buyer/seller
      этого заказа; чужие — 404. `payments` остаётся владельцем
      payment-переходов; `08` расширяет его shipping-статусами после
      архивации `06`.
- [ ] Возвраты и отмена оплаченного заказа — вне скоупа: 409 с
      понятным кодом до отдельного change.

Зависимости: S3-1 и S3-2; одна capability — один активный change,
поэтому `08` идёт после архивации `07`.

### S3-4. Hardening после S2

Change: `09-orders-pagination` (delta `checkout-orders`).
Зачем: закрыть долги, которые мешают росту заказов и мобильному
продавцу.

AC:
- [ ] `GET /orders/mine` и `GET /seller/orders` — cursor-пагинация
      `(created_at, id)`, `limit` 20, `nextCursor`; новые вставки не
      дублируют и не пропускают заказы.
- [ ] UI листает заказы без потери фильтров; пустая страница и конец
      списка обработаны.
- [ ] Точка входа продавца в header на <lg; badge корзины проверяется
      по content-box; axe на изменённых страницах — 0.
- [ ] `pnpm verify`, e2e, LCP preview <2500 ms зелёные.

Без spec change: мобильная точка входа и badge-тест — UI/тестовая
правка.

## Циклы

1. Planning: план, `06-payments` proposal/spec/design/tasks, review,
   `openspec validate --strict`. Код не пишем.
2. Payments foundation (PR A): миграция, контракты, крипто, адаптер,
   fake, down SQL. Ревью и merge.
3. Payments flow (PR B): аккаунт, платёж, вебхук, reconcile, UI, e2e.
4. Delivery: change `07`, товарные габариты, адрес, адаптер, UI;
   после архивации `06`.
5. Lifecycle: change `08`, переходы, история, UI; после архивации
   `07`.
6. Hardening/close: change `09`, пагинация, мобильный вход, badge,
   axe, e2e/LCP, retro, архив changes.

## Риски

- Партнёрская схема ЮKassa может потребовать договор/API, которых
  нет; тогда S3-1 останавливается на адаптере и fake, live — после
  владельца.
- СДЭК API и тарифы меняются; контракт фиксируем адаптером и
  fake-сервером.
- Адрес — новые ПДн; без юрпакета реальные данные не собираем.
- Спринт большой; payments идёт двумя PR (foundation/flow), при 15%
  конфликтов/красном main WIP режем S3-4 и переносим в бэклог.
